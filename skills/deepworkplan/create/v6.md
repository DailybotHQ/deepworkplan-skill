# Create — a v6/v7/v8 plan (outcome contract, guarded materialization)

Read this file when creating a plan with the current pack. It covers every
contract generation of the same record layer: **v8 is the default for new
plans on the 8.x pack** (contract `schema` =
`https://deepworkplan.com/schema/plan-contract/v8.json`: the v7 contract —
the v6 contract plus the optional `tasks[].parallel_safe` marker, with a
journal that also records delegation,
[`spec/V7_CONTRACT.md`](../spec/V7_CONTRACT.md) — plus the optional, closed
`autonomy` block, [`spec/LOOP_ENGINEERING.md`](../spec/LOOP_ENGINEERING.md)).
Write an `autonomy` block only for what the developer states (stall budget,
promptable panes, notify targets, whether a brain may act, queue start);
every absent key takes its recorded default, so most plans carry none. An
explicit `v7` request writes
`https://deepworkplan.com/schema/plan-contract/v7.json` and an explicit `v6`
request `https://deepworkplan.com/schema/plan-contract/v6.json`; the rules
below apply unchanged to all three. `materialize` derives the manifest and
journal generation from that URL (a v8 plan uses the v7 manifest and
journal line). Existing plans keep their recorded generation.

A v6 plan is two authored artifacts plus one guarded sequence:

**Plan identity before authoring.** Resolve `dwp_dir` through
`../shared/context.sh`. For v6, convert the requested name to a 2–5-word
lowercase snake_case slug. On a resumed create request, reuse the matching
partial plan only after checking its recorded objective; an ambiguous slug
needs the full folder name or ID. For a new request, claim the next plan folder
exactly once with:

```bash
python3 ../shared/plan_paths.py --plans-dir <dwp_dir>/plans allocate <slug>
```

The helper creates and prints a flat folder such as
`.dwp/plans/PLAN_001_improve_release_docs/`. Its three-digit minimum is
zero-padded; numbers are never reused after a plan is deleted. Use the printed
basename **verbatim** as the plan identifier in markdown, `contract.plan`,
manifest, journal and all later commands. Do not allocate again when resuming
partial materialization: reuse the existing folder. Existing unnumbered plans
stay in place and continue under their recorded lifecycle.

1. **The plan markdown** — `README.md` and task files in the claimed
   `.dwp/plans/PLAN_<id>_<name>/`, exactly as in the recorded flow (T-* ids,
   one objective per task, `Read Before Starting`, `Acceptance Criteria`
   with `AC-*` IDs, and a runnable `Validation` gate).
   Acceptance criteria appear in the plan as `AC-*` ids **and** in the
   contract verbatim — the markdown is what the approval digests, so edit
   it before materializing, never after approval (a changed plan needs a
   new digest; that is refine territory). A plan folder with no markdown
   is not approvable and `materialize` refuses it.
2. **The outcome contract** — a `contract.json` draft **outside** the plan
   folder until materialized (e.g. `.dwp/plans/PLAN_<id>_<name>.contract.json`):
   outcome, `acceptance_criteria` (each with evidence class: an executed
   gate, a controlled pair, or an asserted human sign-off), `invariants`
   with their evaluation boundary, `scope` (allowed command classes,
   touched surfaces), `resource_envelope` with per-limit enforcement and
   optional reserves, `scheduling`, `permissions`. Authorship guidance and
   the closed field set: [`spec/V6_CONTRACT.md`](../spec/V6_CONTRACT.md).
   A shipped working shape: [`../examples/V6_PLAN_EXAMPLE.md`](../examples/V6_PLAN_EXAMPLE.md).
   Each `gate_intent` `check` is the exact command its gate runs, and its
   first word MUST be a declared command class — wrap shell builtins,
   `VAR=value` prefixes and compound commands as `bash -c '…'` with
   `bash` declared (a check for an asserted-only criterion describes the
   human check and is not run). Command classes are an allowlist of entry
   points, **not a sandbox**: a shell-run check can chain commands, so the
   contract's scope and its review are the control. Validate before proposing: `python3
   ../shared/contract_v6.py validate-contract <draft.json>` — it refuses
   checks the gate runner would refuse and criteria nothing can close
   (`--help` lists `--parent` for revisions); `materialize` refuses the same.
3. **Materialization** (guarded, resumable — manifest, then contract, then
   approval):

```bash
python3 ../shared/ledger.py --plan <dir> materialize --contract <draft.json> \
  [--authority <who>] [--mechanism plan_authorship|pre_authorization] [--note <text>]
```

The helper — never the model's hands — writes `manifest.json` (the
contract pointer that makes the plan's v6-ness discoverable even if the
sequence is interrupted), stamps the content-addressed `contract.json`
into the plan folder, and appends the **first journal event**: the
`approval` citing the contract id and the plan-markdown digest. Only that
event opens the task-start gate; a hand-copied contract without it is
refused at `start` (exit 3), and a manifest whose pointer does not match
the materializing contract is refused rather than rewritten.

`mechanism` is the honest record of how authority was granted:
`plan_authorship` (the human authored or reviewed the plan+contract
before execution) or `pre_authorization` (a standing grant with a stated
envelope — trust mode). Both modes gate identically (A2/A3); what differs
is the recorded authority, never the checks. `--authority` names the
human; an honest name beats a precise one. Authority an agent relays from the
developer says so (`relayed by <agent>`), and the developer's own words are
kept verbatim in a note inside the plan folder — never in scratch space.
The same holds for the **request itself**, relayed or not: every plan keeps
the human's request verbatim in `analysis_results/HUMAN_NOTE.md`. Which text
governs is fixed: **the approved contract binds**; the verbatim request is
the reference it was derived from. A later disagreement between the two is
resolved by an amendment through refine, never by re-reading the request
over the contract. Delegates receive pointers to the note, not paraphrases.

**The plan queue (when the developer asks to queue the plan, or a v8
contract records `autonomy.queue` other than `none`).** After `materialize`
succeeds (the approval exists), append the plan to the repository's queue so
the herdr-peers loop starts it when it is ready
([`../spec/LOOP_ENGINEERING.md`](../spec/LOOP_ENGINEERING.md) §4); `--start`
is the contract's `autonomy.queue` when it records one:

```bash
python3 ../shared/queue.py --dwp <dwp_dir> append --plan <PLAN_id> --lead <address> \
  [--after <PLAN_id>] [--start prompt-lead|launch]
```

`--lead` is the pane the daemon prompts to start the plan: the one the
developer names, or else, inside Herdr, your own — pass `$HERDR_PANE_ID` as
it is (the helper accepts a pane id such as `w9:p1` or a full address such
as `local:w9:p1`). If the helper refuses it, take your row's address from
`herdr-peers list` or ask the developer, and retry with `--lead`. Append
without a lead only when no address is known yet: the item then waits (the
daemon reports it as `no lead named`) until the developer or the lead names
one with
`python3 ../shared/queue.py --dwp <dwp_dir> set-lead --plan <PLAN_id> --lead <address>`.

`--after` names a plan already in the queue that must complete first. A
`prompt-lead` start makes the daemon prompt the named lead once; a `launch`
start is recorded but not started (launching is not available yet). The
helper is the only writer the flows use: never edit `queue.json` by hand from
a flow. Not queuing is the default and always correct.

**v7: marking `parallel_safe` and granting delegation.** Mark a task
`"parallel_safe": true` only when **all** hold: the repository enables a
delegation addon (`python3 ../shared/config.py enabled --repo <repo>` lists
`agentkit` or `herdr`); the task's touched surface does not overlap a
sibling that could be in progress at the same time; it declares a bounded
output; its gates run in this plan; and it shares no interface (schema,
migration, generated artifact, lockfile) with a concurrent sibling —
`validate-contract` warns on overlaps. Otherwise omit the field — absent
is false, and with no delegation addon the marker is noise. Grant
`agent_delegation` only when the developer accepts delegation for this
plan (trust mode records it as part of the pre-authorization); a marker
without the grant authorizes nothing (`../spec/V7_CONTRACT.md` §2). A
delegation transport may launch delegates with the agent CLI's elevated
permissions: before recording the grant, read the enabled transport
addon's permissions note and tell the developer what it means.

**v7: decision debates.** When `config.py enabled` lists `herdr`,
`config.py show` resolves `decisions.debate` to `auto`, the developer
accepts the `agent_delegation` grant for this plan, and the analysis
finds a consequential decision (two viable options with materially
different outcomes, hard to reverse or cross-cutting, settled by nothing in
the repository), read [`decisions.md`](decisions.md) and plan it as a
decision task. Otherwise read nothing more: decisions stay the agent's own
record.

Interrupted materialization (manifest without contract, contract without
approval) → re-run the same command with the same inputs; it resumes and
says so. A **different** contract for a materialized plan is never
written over the old one — that is a revision, the refine amendment path
(`contracts/` chain, fresh approval).

**The `PROGRESS.md` header (v8).** Right after `materialize`, give the
plan's `PROGRESS.md` its structured header (spec
[`LOOP_ENGINEERING.md`](../spec/LOOP_ENGINEERING.md) §3.2) — four fixed
lines under the title that the loop, the fleet and `resume` read instead of
prose:

```bash
python3 ../shared/progress_header.py --plan <dir> \
  --goal "<the plan's goal, one line>" --next "<the first action, one line>"
```

`Current task` and `Needs` are derived from the records, so the header can
never claim a state the journal does not hold; the body below it stays the
working index the recorded flow describes. v6 and v7 plans skip this step.

After materialization: report the contract id and the plan digest back,
and route to **execute** (the v6 loop). Never auto-execute; the create
flow ends at the approval event, exactly as in guided mode.

Lite v6: same sequence, a single-task contract with the essential
criteria (the fixtures show the floor). Lite is a representation choice,
not a weaker gate — every criterion still closes only on its evidence
class.
