# Create — a v6 plan (outcome contract, guarded materialization)

Read this file only when creating a plan under the **v6 candidate**: the
pack's line is 6+ or the developer explicitly asked for v6 (an explicit
candidate request overrides a 5.x line). Otherwise the recorded create
flow above applies — this pack never silently produces a v6 plan, and
never presents v6 as the default.

A v6 plan is two authored artifacts plus one guarded sequence:

**Plan identity before authoring.** Resolve `dwp_dir` through
`../shared/context.sh`. For v6, convert the requested name to a 2–5-word
lowercase snake_case slug. On a resumed create request, reuse the matching
partial plan only after checking its recorded objective; an ambiguous slug
needs the full folder name or ID. For a new request, claim the next plan folder
exactly once with:

```bash
python3 ../shared/plan_paths.py --plans-dir <dwp_dir>/plans allocate <slug>
```

The helper creates and prints a flat folder such as
`.dwp/plans/PLAN_001_improve_release_docs/`. Its three-digit minimum is
zero-padded; numbers are never reused after a plan is deleted. Use the printed
basename **verbatim** as the plan identifier in markdown, `contract.plan`,
manifest, journal and all later commands. Do not allocate again when resuming
partial materialization: reuse the existing folder. Existing unnumbered plans
stay in place and continue under their recorded lifecycle.

1. **The plan markdown** — `README.md` and task files in the claimed
   `.dwp/plans/PLAN_<id>_<name>/`, exactly as in the recorded flow (T-* ids,
   one objective per task, `Read Before Starting`, `Acceptance Criteria`
   with `AC-*` IDs, and a runnable `Validation` gate).
   Acceptance criteria appear in the plan as `AC-*` ids **and** in the
   contract verbatim — the markdown is what the approval digests, so edit
   it before materializing, never after approval (a changed plan needs a
   new digest; that is refine territory). A plan folder with no markdown
   is not approvable and `materialize` refuses it.
2. **The outcome contract** — a `contract.json` draft **outside** the plan
   folder until materialized (e.g. `.dwp/plans/PLAN_<id>_<name>.contract.json`):
   outcome, `acceptance_criteria` (each with evidence class: an executed
   gate, a controlled pair, or an asserted human sign-off), `invariants`
   with their evaluation boundary, `scope` (allowed command classes,
   touched surfaces), `resource_envelope` with per-limit enforcement and
   optional reserves, `scheduling`, `permissions`. Authorship guidance and
   the closed field set: [`spec/V6_CONTRACT.md`](../spec/V6_CONTRACT.md).
   A shipped working shape: [`../examples/V6_PLAN_EXAMPLE.md`](../examples/V6_PLAN_EXAMPLE.md).
   Validate before proposing: `python3
   ../shared/contract_v6.py validate-contract <draft.json>`.
3. **Materialization** (guarded, resumable — manifest, then contract, then
   approval):

```bash
python3 ../shared/ledger.py --plan <dir> materialize --contract <draft.json> \
  [--authority <who>] [--mechanism plan_authorship|pre_authorization] [--note <text>]
```

The helper — never the model's hands — writes `manifest.json` (the
contract pointer that makes the plan's v6-ness discoverable even if the
sequence is interrupted), stamps the content-addressed `contract.json`
into the plan folder, and appends the **first journal event**: the
`approval` citing the contract id and the plan-markdown digest. Only that
event opens the task-start gate; a hand-copied contract without it is
refused at `start` (exit 3), and a manifest whose pointer does not match
the materializing contract is refused rather than rewritten.

`mechanism` is the honest record of how authority was granted:
`plan_authorship` (the human authored or reviewed the plan+contract
before execution) or `pre_authorization` (a standing grant with a stated
envelope — trust mode). Both modes gate identically (A2/A3); what differs
is the recorded authority, never the checks. `--authority` names the
human; an honest name beats a precise one.

Interrupted materialization (manifest without contract, contract without
approval) → re-run the same command with the same inputs; it resumes and
says so. A **different** contract for a materialized plan is never
written over the old one — that is a revision, the refine amendment path
(`contracts/` chain, fresh approval).

After materialization: report the contract id and the plan digest back,
and route to **execute** (the v6 loop). Never auto-execute; the create
flow ends at the approval event, exactly as in guided mode.

Lite v6: same sequence, a single-task contract with the essential
criteria (the fixtures show the floor). Lite is a representation choice,
not a weaker gate — every criterion still closes only on its evidence
class.
